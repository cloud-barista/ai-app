# 실제 클라우드 시험 결과 (2026-11-03)

> 읽는 사람: AI-App 을 부르는 기관 개발자(ETRI, BESP, 경희대)와 이 repo 를 고치는 사람.
> 무엇을 어떤 순서로 돌렸고, 무엇이 막혔고, 무엇을 고쳤는지를 적습니다. 숫자는 그날 배포 기록(`GET /aiapp/deployments`)에서 뽑았습니다.

## 1. 한 줄 요약

ETRI 여행 포털 시나리오의 노드 3대(vm1, vm2, vm3)를 실제 GPU VM 으로 만들고, AI-App API 만으로 추론 서비스 3개와 응용 3개를 올렸습니다. 6개 모두 바깥에서 응답했습니다. 그 과정에서 AI-App 쪽 결함 4건과 예시 응용 결함 1건이 나와 고쳤습니다.

## 2. 환경

| 항목 | 값 |
|---|---|
| AI-App | 이 repo main (`a3ddf2c` 에서 시작, 시험 중 고친 커밋은 6절). `ai-app-server` 를 로컬 컨테이너로 띄움 |
| Semaphore | `semaphoreui/semaphore:v2.12.17`, 로컬 컨테이너. playbook 폴더 `deploy/ansible` 을 그대로 마운트 |
| CB-Tumblebug | 0.13.8 (cb-spider 0.13.20), 로컬. namespace `aiapp-test`, Infra `travel` |
| 노드에서 바깥으로 | 노드가 Docker Hub, ghcr.io, Hugging Face, registry.ollama.ai, GitHub 에 직접 나감 |
| 확인 방법 | 이 repo 를 돌린 PC 에서 노드 공인 IP 로 직접 호출. 노드 안은 Tumblebug SSH 키로 읽기만 함 |

gcp 는 쓰지 못했습니다. 등록된 서비스 계정에 Compute 권한이 없어 스펙 조회부터 막혔습니다(`Error 403: Required 'compute.machineTypes.list' permission`). 그래서 vm3 도 aws 에 만들었습니다. 노드 위에서 도는 것은 CSP 와 관계없이 같습니다.

## 3. 노드

| 노드 | CSP·리전 | 스펙 | GPU | 이미지 | 드라이버 |
|---|---|---|---|---|---|
| vm1-2 | aws ap-northeast-1 | `g4dn.xlarge` | T4 16GB | Deep Learning Base OSS Nvidia Driver GPU AMI (Ubuntu 22.04) `ami-0e8e3e0f677c0f395` | 595 |
| vm2b-2 | azure koreacentral | `Standard_NC4as_T4_v3` | T4 16GB | `microsoft-dsvm:ubuntu-hpc:2204:22.04.2026100101` | 580 |
| vm3-2 | aws ap-northeast-1 | `g6.xlarge` | L4 24GB | vm1 과 같은 AMI | 595 |

- aws 서울(ap-northeast-2)은 계정의 VPC 한도에 걸려 만들지 못했습니다(`VpcLimitExceeded`). 도쿄로 옮겼습니다.
- azure 의 처음 vm2(`vm2-1`, 이미지 `microsoft-dsvm:ubuntu-2204:2204-gen2:25.06.18`)는 드라이버가 535 라서 Ollama 가 GPU 를 쓰지 못했습니다(5절). 새 이미지로 vm2b 를 만들고 vm2-1 은 내린 뒤 지웠습니다.
- Tumblebug 사전 검토(`infraDynamicReview`, `nodeGroupDynamicReview`)의 예상 비용은 vm1 $0.71, vm2 $0.647, vm3 $1.1672 (시간당)입니다.

## 4. 결과

| 노드 | 무엇 | 배포 요청 | 걸린 시간 (install-docker / 기동) | 바깥에서 본 것 |
|---|---|---|---|---|
| vm1-2 | vLLM + Qwen3-Embedding-0.6B | `inference`, `runtimeId: vllm`, `gpu: true` | 36초 / 1,146초 | `/v1/embeddings` 가 1024차원 벡터를 돌려줌 |
| vm1-2 | Dify | `app`, `env.VLLM_BASE_URL` | 41초 / 221초 | `/install` 200 |
| vm2b-2 | Ollama + Qwen3-VL-8B (`qwen3-vl:8b`) | `inference`, `runtimeId: ollama`, `gpu: true` | 61초 / 401초 | GPU 메모리 6.8GB, 초당 약 43 토큰 |
| vm2b-2 | Open WebUI | `app`, `env.OLLAMA_BASE_URL` | 11초 / 186초 | `/` 200, `/api/config` 의 version 0.12.4 |
| vm3-2 | vLLM + Ministral 3 8B (FP8) | `inference`, `args: ["--max-model-len","32768", ...]` | 16초 / 176초 | 영어·한국어 대화 응답 (5절의 온도 조건) |
| vm3-2 | Langflow | `app`, `env.MODEL_BASE_URL`, `env.LANGFLOW_SUPERUSER_PASSWORD` | 16초 / 31초 | `/health` 200 |

- 기동 시간에는 런타임 이미지와 모델을 처음 받는 시간이 들어 있습니다. vm1 의 vLLM 이 길었던 것은 vLLM 이미지가 크기 때문으로 보입니다(나눠 재지 않았습니다).
- vm3 의 기동 176초는 같은 노드에 두 번째로 띄운 것이라 이미지·가중치를 다시 받지 않았습니다. 처음 시도는 실패했고 1,376초가 걸렸습니다(5절).

같이 확인한 기능입니다.

| 기능 | 확인한 것 |
|---|---|
| 포트 열기 | 배포가 끝난 뒤 노드 보안 그룹에 `8000`, `80`, `11434`, `3000`, `7860` 이 TCP inbound `0.0.0.0/0` 로 들어감. Tumblebug `GET /ns/aiapp-test/resources/securityGroup/{id}` 로 규칙을 읽어 봄. 같은 포트로 다시 배포하면 `existing` 으로 남고 다시 보내지 않음 |
| 주소 조회 | `GET /aiapp/endpoints?nsId=aiapp-test` 가 노드 3대의 추론 3개, 응용 3개를 돌려줌. 모두 `portsOpened: true` |
| 내리기 | vm2-1 의 Ollama 배포를 `DELETE /aiapp/deployments/{id}` 로 내림. 202 뒤 `compose-down` 성공, 상태 `removed`, 주소 목록에서 빠지고 포트가 응답하지 않음 |
| 상태 | `GET /aiapp/status` 가 Semaphore(v2.12.17, 인증 됨), Tumblebug(ready), 공유 저장소(쓰기 됨)를 보여 줌 |
| Semaphore 링크 | 배포 단계마다 `taskUrl` (`http://<Semaphore 화면>/project/1/history?t=<태스크>`) 이 기록됨 |
| Running 직후 배포 | vm2b-2 는 VM 이 Running 이 되자마자 배포를 보냈고 성공함 |

## 5. 막힌 것과 원인

| # | 증상 | 원인 | 어떻게 했나 |
|---|---|---|---|
| 1 | vm1 첫 배포가 `cb-user@...: Permission denied (publickey)` 로 실패 | VM 이 Running 이 된 직후라 cloud-init 이 접속 사용자를 아직 만들지 않음. 몇 분 뒤 같은 키로 접속됨 | `install-docker` 가 처음에 접속될 때까지 최대 10분 기다리게 고침 (`1101793`) |
| 2 | vm2 에서 `docker is installed but "docker compose" is not available` 로 멈춤 | azure DSVM 이미지에 docker(moby-engine 24.0.9)는 있고 compose 플러그인은 없음 | 노드 apt 저장소의 `docker-compose-plugin` 이나 `moby-compose` 를 깔게 고침 (`1101793`) |
| 3 | vm2 에서 docker 런타임이 `runc` 뿐 | 이미지에 `nvidia-ctk` 가 이미 있으면 nvidia 런타임 등록을 건너뜀 | docker 런타임 목록에 nvidia 가 없으면 항상 등록하게 고침 (`1101793`) |
| 4 | vm2-1 의 Ollama 가 대화를 300초 안에 못 끝냄 | 드라이버 535. Ollama 0.40.13 로그 `NVIDIA driver too old ... required_driver="550 or newer"`, GPU 메모리 2MiB, CPU 로 초당 5.4 토큰 | 드라이버 580 인 새 이미지로 vm2b 를 만듦. 배포는 `succeeded` 로 나와서 기록만으로는 알 수 없었음(7절) |
| 5 | vm3 의 Ministral 이 기동 중 멈춤 | vLLM 이 최대 문맥 262,144 를 잡아 KV 캐시 34 GiB 가 필요한데 L4 에서 9.31 GiB 만 남음 (`ValueError: ... estimated maximum model length is 71760`) | 추론 배포에 런타임 인자 `args` 를 추가함 (`f1740de`). `--max-model-len 32768` 로 다시 배포해서 뜸 |
| 6 | Ministral 이 한국어 질문에 여러 언어가 섞인 글을 냄 | 기본 샘플링 온도. `temperature: 0.1` 과 system 프롬프트를 주니 바른 한국어 답이 나옴. 영어 질문은 온도와 관계없이 `Paris` 로 바로 답함 | 코드는 고치지 않음. 부르는 쪽(Langflow, 포털)이 온도를 낮게 줘야 함. 두 번째 배포에 Mistral 형식 인자(`--tokenizer-mode mistral --config-format mistral --load-format mistral`)도 넣었는데, 이것이 결과를 바꿨는지는 나눠 보지 않음 |
| 7 | Langflow 컨테이너가 계속 다시 시작됨, 배포는 `succeeded` | Langflow 1.13.0 은 `LANGFLOW_SUPERUSER_PASSWORD` 없이 시작하지 않음 | 예시 번들이 비밀번호를 env 로 받게 고침 (`e3309e0`), 버전 2 로 다시 올려 배포 |
| 8 | Qwen3-VL-8B 가 1,500 토큰을 써도 답(`content`)이 비어 있음 | 모델이 생각(thinking)을 길게 씀. `"think": false` 를 줘도 `message.thinking` 으로 나옴 | 코드는 고치지 않음. 짧은 답이 필요하면 토큰 수와 시간 제한을 넉넉히 두거나 모델을 바꿔야 함 |
| 9 | 없는 노드 ID 로 배포하면 202 를 받은 뒤 실패 | 요청을 받을 때 노드를 확인하지 않고, Tumblebug 이 없는 노드에 404 가 아니라 500 을 줌 | 요청을 받을 때 노드를 읽어 없으면 404 로 거절하게 고침(7절). Tumblebug 의 500 `no Node found` 도 없는 노드로 읽음 |

## 7. 남은 것

| 문제 | 왜 문제인가 | 상태 |
|---|---|---|
| 모델마다 필요한 런타임 인자를 부르는 쪽이 알아야 함 | Ministral 은 `--max-model-len` 없이는 L4 에서 뜨지 않음. ETRI·AI-Web 이 vLLM 인자를 몰라도 되게 하려면 카탈로그 아티팩트에 기본 인자를 두는 방법이 있음 | 정하지 않음 |
| GPU 를 요청했는데 CPU 로 돌아도 `succeeded` | vm2-1 처럼 느려서 쓸 수 없는데 기록으로는 모름 | 정하지 않음 |
| 응용 배포는 script 가 끝나면 `succeeded` | 서비스가 실제로 응답하는지 기다리지 않음. Open WebUI 는 성공 직후 약 20초 응답하지 않았고, Langflow 는 계속 다시 시작하는데도 `succeeded` 였음 | 정하지 않음 |
| 배포 env 가 평문으로 남음 | Langflow 비밀번호가 배포 기록, 노드의 `.env`, 공유 저장소 폴더에 그대로 남음 | 설계 문서 8절에 이미 있는 문제 |
| 없는 노드 ID 를 요청 시점에 거절하지 않음 | 부르는 쪽이 202 를 받고 나중에야 실패를 앎 | 고침. `POST /deployments` 가 받기 전에 노드를 읽어 없으면 404, CB-Tumblebug 이 실패하면 502 |
| 응용 안에서 모델을 실제로 부르는 것 | Dify·Open WebUI·Langflow 화면이 열리는 것까지만 봄. 각 응용에서 모델 공급자를 설정하고 답을 받는 것은 하지 않음 | 하지 않음 |
| docker 가 없는 이미지 | 세 이미지 모두 docker 가 들어 있어서, Docker 저장소에서 처음부터 까는 분기는 실제 VM 에서 돌지 않음 | 하지 않음 |
| gcp | 서비스 계정 Compute 권한 | 권한이 정리되면 시험 |
