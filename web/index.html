이 프로토타입이 하는 일

이노그리드 담당 영역은 AI-App 서비스(AI 응용 등록·버전, 라이프사이클, 모니터링)와 자동배포/자동제어 엔진입니다. 두 프로세스 모두 LLM 을 쓰지 않습니다. 엔진은 구조화된 요청을 받아 정해진 순서로 AI-App 의 도구를 부르고, 단계마다 무엇을 불렀고 무엇이 돌아왔는지 기록합니다. 자연어 해석과 인프라 추천은 협력 기관 담당 영역이라 여기에는 연동을 확인하는 모의 구현만 있습니다.

응용 등록·버전과 라이프사이클

모델 서비스와 그것을 쓰는 AI 응용을 메타데이터로 등록하고, 같은 id 로 다시 올리면 새 버전이 됩니다. 배포·업데이트·정지·재개·재부팅·종료를 AI-App 이 맡습니다.

자동배포/자동제어 엔진

deploy · heal · control · status 워크플로를 정해진 순서로 실행합니다. AI 응용이 모델 서비스를 필요로 하면 모델 서비스부터 올립니다. 다음 단계는 앞 단계의 결과로 정하고, 모델이 정하지 않습니다.

쓰기는 기본적으로 막혀 있다

배포·제어·삭제는 등급이 붙어 있고, dry-run 이 켜져 있으면 계획과 검토까지만 하고 멈춥니다. 엔진은 막힌 단계를 "차단됨", 그 결과가 있어야 하는 다음 단계를 "선행 단계 대기" 로 남깁니다.

모니터링: 만들어진 것과 쓸 수 있는 것은 다르다

노드가 Running 이라고 응용이 답하거나 가속기를 쓸 수 있다는 뜻이 아닙니다. 노드 안에서 서빙 포트에 직접 묻고, 가속기를 직접 읽어 카탈로그의 약속과 대조합니다.

응용 카탈로그

AI 응용 메타데이터 규격을 실물로 본 것입니다. 런타임 축과 가속기 축이 서로 다른 필드라는 것이 핵심이고, AI 응용은 requires 로 먼저 떠 있어야 할 모델 서비스를 적습니다.

배포와 라이프사이클

  

    AI-App 의 배포 API 를 직접 부르는 화면입니다. 여기서 부르는 것은 전부 실제 호출이고,
    이종 클라우드 관리 계층이 붙어 있지 않으면 실패 응답이 그대로 보입니다. 그것도 동작의 일부라 감추지 않습니다.
  


  

    
배포 계획 클라우드에 아무것도 만들지 않습니다

    

      

        
        
      

      

        
        
      

      

        
        
      

    

    

      

        "계획만 만들기" 는 AI-App 의 단일 응용 계획입니다. 고른 응용 하나의 스펙·이미지·설치 명령만 정합니다.
        AI 응용이 필요로 하는 모델 서비스까지 순서대로 올리는 것은 자동화 엔진의 deploy 워크플로입니다.
      

      
    

    

    

    

  


  

    
배포 목록

    

      

      
    

    

    

  


  

    
이 화면에 쓰기 버튼이 없는 이유

    

      실제 생성·제어·삭제 버튼을 이 화면에는 의도적으로 넣지 않았습니다.
      되돌릴 수 없고 과금되는 행동을 화면의 버튼 하나에 걸어 두지 않는 것이 이 프로토타입의
      안전장치와 같은 취지입니다. 생성·제어는 API 를 직접 부르거나 자동화 엔진의 워크플로로 하고,
      엔진 화면은 dry-run 이 꺼져 있으면 실행 전에 한 번 더 묻습니다.
      서빙 상태와 가속기 판독은 모니터링 화면에 있습니다.
    

  







  
모니터링

  

    배포된 응용이 실제로 답하는지와 노드의 가속기를 실제로 쓸 수 있는지를 노드 안에서 직접 확인합니다.
  


  

    
대상

    

      

        
        
      

      

        
        
      

    

    

      

      
    

  


  

    
서빙 상태 확인 노드가 떴다고 응용이 답하는 것은 아닙니다

    

      

      
    

    

    

    

      각 노드 안에서 curl 로 127.0.0.1:<서빙 포트><헬스 경로> 를 한 번 부릅니다.
      방화벽이나 공인 IP 와 무관하게 서버 프로세스가 답하는지만 봅니다.
      2xx·3xx 면 준비됨이고, 모든 노드가 준비돼야 배포가 준비됨입니다.
      응용은 배포 이름의 ai-mcmp.app-id 라벨로 찾습니다.
    

  


  

    
가속기 판독 만들어진 것과 쓸 수 있는 것은 다릅니다

    

      

      
    

    

    

    

      노드에서 PCI 버스를 먼저 읽고, 벤더 도구(nvidia-smi·rocm-smi·
      rbln-stat·furiosa-smi·hl-smi·tpu-info)가
      있으면 그 위에 덧칠합니다. 버스는 아무것도 설치돼 있지 않아도 답하므로,
      드라이버가 안 붙은 장치와 아예 없는 장치를 가를 수 있습니다.
    

  

  






  
도구와 게이트 (MCP)

  

    MCP 도구는 두 층입니다. 자동화 엔진이 여는 상위 도구를 자연어 에이전트와 외부 에이전트가 부르고,
    엔진은 그 안에서 AI-App 이 여는 기능 도구를 부릅니다.
    등급이 곧 안전장치이고, 실행 여부는 서비스 설정이지 부르는 쪽의 판단이 아닙니다.

연동 지점

    

      이노그리드 쪽 계약은 엔진의 MCP 도구와 엔진 기술서(GET /engine/card)입니다.
      모의 에이전트는 그 도구를 부르는 MCP 클라이언트이고, 도구가 돌려준 엔진 실행 ID 를 단계마다 남깁니다.
      엔진 실행 ID 를 누르면 자동화 엔진 화면에서 그 실행의 단계를 봅니다.

인프라 추천 모의

  

    AI-App 은 추천을 직접 하지 않고 AIAPP_RECOMMENDER_URL 의 추천 API 를 부릅니다.
    여기서 보는 후보는 그 API(지금은 모의 구현)가 돌려준 것입니다.
  


  

    
스펙 후보

    

      
      
      
    

    

    

    

    

  


  

    
계약 요약 이노그리드가 제안한 계약. 요청에 AppSpec 을 그대로 실어 보냅니다

    

      
호출요청응답

      

        POST /recommendations/specs
        { app: AppSpec, limit }
        { candidates: [ { id, providerName, regionName, acceleratorType,
          acceleratorModel, acceleratorCount, acceleratorMemoryGB, vCPU, memoryGiB, costPerHour } ], reason }
      

      

        POST /recommendations/image
        { app: AppSpec, specId }
        { imageId, source, reason }
      

    

    

      AI-App 은 첫 후보를 계획에 쓰고 계획에 specSource: recommended:remote,
      imageSource: resolved:remote 로 남깁니다.
      추천 API 가 설정되지 않으면 요청에 specId 와 imageId 를 직접 지정해야 하고,
      아니면 422 로 실패합니다.
