이 프로토타입이 하는 일

이노그리드 담당 영역은 AI-App 서비스(모델 카탈로그, 응용 업로드·버전, 노드 배포와 제어)와 자동배포/자동제어 엔진입니다. 두 프로세스 모두 LLM 을 쓰지 않습니다. 엔진은 구조화된 요청을 받아 정해진 순서로 AI-App 의 도구를 부르고, 단계마다 무엇을 불렀고 무엇이 돌아왔는지 기록합니다. 자연어 해석과 인프라 추천은 협력 기관 담당 영역이라 여기에는 연동을 확인하는 모의 구현만 있습니다.

모델 카탈로그와 응용 업로드

같은 모델도 출처마다 다른 형태로 배포되므로 포맷·정밀도·호환 엔진은 모델이 아니라 아티팩트에 둡니다. 응용은 파일과 노드에서 돌릴 스크립트를 이름으로 올리고, 같은 이름으로 다시 올리면 새 버전이 됩니다.

자동배포/자동제어 엔진

deploy · heal · control · status 워크플로를 정해진 순서로 실행합니다. deploy 는 배포 요청을 받아 모델이나 응용을 확인하고, 배포를 만들고, 모든 노드가 끝날 때까지 따라갑니다. 다음 단계는 앞 단계의 결과로 정하고, 모델이 정하지 않습니다.

쓰기는 기본적으로 막혀 있다

dry-run 이 켜져 있으면 배포는 노드 조회와 파일 배치까지만 하고 Semaphore 에 아무것도 등록하지 않으며, 노드 제어는 막힙니다. 엔진은 막힌 단계를 "차단됨", 그 결과가 있어야 하는 다음 단계를 "선행 단계 대기" 로 남깁니다.

배포 기록이 상태의 출처

노드마다 상태와 Semaphore 태스크 결과를 배포 기록에 남기고, 태스크 로그는 따로 받습니다. 모델 서비스가 답하는지는 배포 안에서 compose-up 플레이북이 노드에서 직접 확인합니다.

모델 카탈로그

같은 모델이 출처마다 다른 형태로 배포됩니다(HF 의 safetensors, Ollama 의 GGUF). 그래서 포맷·정밀도·호환 엔진은 아티팩트에 있고, 모델 서비스 배포는 모델 하나와 그 아티팩트 하나, 엔진 하나를 고릅니다.

응용

AI 응용은 파일과 노드에서 돌릴 스크립트입니다. 같은 이름으로 다시 올리면 새 버전이 되고, 배포하면 파일이 노드의 한 폴더로 복사되고 그 폴더에서 스크립트가 돕니다. 다른 노드의 주소 같은 값은 등록이 아니라 배포 요청의 env 로 줍니다.

노드 배포와 제어

CB-Tumblebug 이 이미 띄운 노드에 모델 서비스나 올린 응용을 배포합니다. AI-App 이 노드 정보와 SSH 키를 읽고, 파일을 공유 저장소에 둔 뒤 Semaphore 로 플레이북을 돌립니다. dry-run 이 켜져 있으면 조회와 파일 배치까지만 하고 만든 compose 를 돌려줍니다. 부르는 것은 전부 실제 호출입니다.

상태별 배포

부르는 중...

노드별 작업 같은 노드의 같은 작업 키는 나중 배포가 앞 배포를 바꿉니다

작업 키는 모델 서비스면 ms-<engine>, 응용이면 app-<name> 이고, 노드 폴더 /opt/aiapp/<작업 키> 와 compose 프로젝트 aiapp-<작업 키> 를 정합니다. 배포 기록에 workKey 가 없으면 요청에서 같은 규칙으로 계산해 계산 을 붙입니다.

서빙 응답과 가속기는 어디서 보나

예전 화면의 배포(Infra) 단위 서빙 응답 확인과 가속기 판독은 AI-App 에서 빠졌습니다. 지금은 모델 서비스가 답하는지를 배포 안에서 compose-up 플레이북이 노드에서 직접 확인하고, 그 결과가 노드의 단계 상태와 로그로 남습니다. 자동화 엔진의 status 워크플로가 배포 기록과 노드별 마지막 로그 줄을 한 번에 읽습니다.

도구와 게이트 (MCP)

MCP 도구는 두 층입니다. 자동화 엔진이 여는 상위 도구를 자연어 에이전트와 외부 에이전트가 부르고, 엔진은 그 안에서 AI-App 이 여는 기능 도구를 부릅니다. 등급이 곧 안전장치이고, 실행 여부는 서비스 설정이지 부르는 쪽의 판단이 아닙니다.

연동 지점

    

      이노그리드 쪽 계약은 엔진의 MCP 도구와 엔진 기술서(GET /engine/card)입니다.
      모의 에이전트는 그 도구를 부르는 MCP 클라이언트이고, 도구가 돌려준 엔진 실행 ID 를 단계마다 남깁니다.
      엔진 실행 ID 를 누르면 자동화 엔진 화면에서 그 실행의 단계를 봅니다.

          resources: { minVCPU, minMemoryGiB }, install: { osType } }, limit }
        { candidates: [ { id, providerName, regionName, acceleratorType,
          acceleratorModel, acceleratorCount, acceleratorMemoryGB, vCPU, memoryGiB, costPerHour } ], reason }

        { imageId, source, reason }
      

    

    

      모의 구현은 토큰(AIAPP_MOCK_RECOMMENDER_TOKEN)이 설정돼 있으면 모든 요청에 Bearer 토큰을 요구하고,
      reason 앞에 [partner mock] 을 붙여 진짜 추천처럼 읽히지 않게 합니다.
